# Arc Llama 1.0 release plan

## Goal

Arc Llama 1.0 should make local inference on a supported Intel Arc system feel
predictable: install the package, select a GGUF, run one command, and receive
clean OpenAI-compatible responses. Failures should explain what the user can do
next without requiring them to interpret `llama-server` logs.

The 1.0 release is a stability promise for the core single-GPU product. It is
not a promise that every optional or experimental feature is finished.

## Supported scope for 1.0

The following capabilities are release-blocking:

- Windows 10/11 x86-64 and Linux x86-64.
- Python 3.10 through 3.14.
- Intel Arc Alchemist, Battlemage, and Lunar Lake GPUs recognized by
  `arc-llama gpus`.
- Vulkan as the portable default and SYCL when a compatible Intel oneAPI and
  `llama-server` installation is available.
- One local GPU with automatic model loading and the configured residency
  policy.
- Local GGUF paths and Hugging Face GGUF specifications.
- `/v1/models`, `/v1/chat/completions`, `/v1/completions`, and
  `/v1/embeddings`.
- Streaming and non-streaming requests.
- The model manager and chat UI working without internet access.
- Safe runtime installation, configuration updates, and community recipe
  updates.

The following remain experimental and do not block 1.0:

- Multi-GPU scheduling.
- Coding agents, MCP tools, and plugins.
- The audio-companion integration contract.
- Speculative strategies beyond the guarded target-only fallback.
- Features implemented only by particular `llama.cpp` builds.

## Release gates

Every gate below must be satisfied before publishing 1.0:

1. A new user can complete the supported first-run paths without editing a
   configuration file by hand.
2. Expected startup failures return a short actionable message and retain
   detailed diagnostics for troubleshooting.
3. Supported chat requests return stable `content` and `reasoning_content`
   fields, and streams terminate correctly.
4. The automated suite, type checks, lint checks, package build, and bare-wheel
   checks pass from the release commit.
5. The supported hardware matrix has recorded results.
6. A public 0.9 release candidate completes the stabilization period with no
   unresolved release-blocking defects.
7. The 1.0 wheel and source distribution contain no local files, secrets,
   caches, or missing runtime assets.

## Phase 1: establish a reviewable release baseline

### Work

- Put the current 0.9 work on a neutral release branch such as
  `release/1.0-prep`.
- Split the working tree into reviewable commits by behavior:
  1. runtime and one-command setup;
  2. GGUF metadata and fit calculation;
  3. recipe and speculative-decoding gates;
  4. web UI and browser safety;
  5. tests, compatibility documentation, and release automation.
- Keep authorship as the maintainer and omit assistant-generated trailers.
- Review the complete diff for debug output, machine-specific paths, copied
  credentials, generated files, and accidental behavior changes.
- Rebuild the virtual environment from the declared project dependencies and
  confirm it reports the project version.

### Acceptance criteria

- `git diff --check` is clean.
- Each commit has one clear purpose and can be reviewed independently.
- The release branch contains all intended local work and no unrelated files.
- `arc-llama --version`, application metadata, wheel metadata, and the
  changelog agree on the development version.

## Phase 2: finish the one-command first-run experience

### Required scenarios

Exercise `arc-llama run` from a clean temporary configuration and state
directory in each of these situations:

1. A local GGUF path is supplied.
2. A local path contains spaces and non-ASCII characters.
3. A Hugging Face repository and filename are supplied.
4. Exactly one discoverable model exists and no source is supplied.
5. Multiple models exist and no source is supplied.
6. A compatible runtime is already configured.
7. No runtime is configured and a verified runtime must be installed.
8. A partial runtime or model download is interrupted and then resumed.
9. The requested model clearly exceeds available GPU memory.
10. No supported Intel GPU is detected.
11. `--setup-only` is used and must not leave a service running.
12. The same command is run twice and must be idempotent.

### Product behavior

- Print the detected GPU, selected backend, runtime source, model source,
  context, KV-cache types, estimated GPU-memory use, and endpoint before
  starting inference.
- Explain every automatic choice in one line and show the exact override when
  a user may reasonably want a different choice.
- Never replace a working runtime, model, registry, or configuration with a
  partial download.
- Leave enough state after interruption that rerunning the same command is
  safe.
- Require explicit confirmation only for choices that can overwrite user data
  or expose the service beyond loopback.

### Acceptance criteria

- All twelve scenarios have automated coverage where hardware is not required.
- A clean-machine walkthrough can be completed without hand-editing TOML.
- Setup failure leaves no orphan `llama-server` process or occupied port.
- The final successful output includes usable API and UI URLs.

## Phase 3: make diagnostics actionable

### Preflight checks

Reject these conditions before starting `llama-server`:

- Missing or unreadable target GGUF.
- Missing or unreadable speculative draft GGUF.
- Missing runtime executable or required sibling libraries.
- Unsupported or incompatible runtime capabilities.
- Invalid GPU assignment or unavailable GPU.
- Port already in use.
- Known model/draft tokenizer incompatibility.
- A recipe that cannot fit within the configured memory policy.

The missing-file case should return a concise response similar to:

> Model file not found: PATH. Update the model path or remove this registration.

It should not start a process and wait for the health timeout.

### Structured failure model

- Introduce stable internal failure categories such as `model_missing`,
  `runtime_missing`, `runtime_incompatible`, `gpu_unavailable`, `port_in_use`,
  `out_of_memory`, `startup_timeout`, and `process_exited`.
- Return a short message, suggested next action, and a diagnostics identifier
  from CLI and admin API failures.
- Preserve the last useful log lines, command parameters with secrets redacted,
  process exit code, backend, GPU, and runtime version.
- Ensure admin API errors use ordinary JSON and an appropriate HTTP status.
- Add a machine-readable `arc-llama doctor --json` mode if diagnostics cannot
  otherwise be collected reliably by support tools.

### Acceptance criteria

- Every expected failure category has a focused test.
- Missing model and draft files fail in under one second without launching a
  child process.
- Error output never includes admin tokens, Hugging Face tokens, or unrelated
  environment variables.
- An unexpected startup failure still includes enough information to locate the
  retained detailed log.
- Arc Llama remains healthy and can load another model after a failed load.

## Phase 4: normalize model responses

Different chat templates and `llama.cpp` builds expose reasoning in different
ways. The 1.0 API needs a stable contract independent of those differences.

### Contract

- `message.content` contains the final user-visible answer when the model
  produces one.
- `message.reasoning_content` contains reasoning only when the upstream runtime
  identifies it as reasoning and the request permits it.
- Disabling reasoning must not move raw thought-channel control markers into
  `content`.
- Arc Llama must not invent a final answer when the model stops during
  reasoning; the finish reason and partial reasoning should remain truthful.
- Streaming deltas follow the same field rules as non-streaming responses and
  end with one finish chunk followed by `[DONE]`.
- Unknown future fields from `llama.cpp` continue to pass through unless they
  conflict with the stable Arc Llama fields.

### Work

- Capture representative response fixtures for ordinary, reasoning, and
  tool-capable chat templates.
- Test `reasoning_format` values supported by the pinned runtime and explicitly
  reject or pass through unsupported values.
- Normalize known channel markers only when the active template and runtime
  provide enough evidence to do so safely.
- Test low token limits, empty content, reasoning-only output, stop sequences,
  client cancellation, upstream disconnects, and malformed stream chunks.
- Run the same prompts directly against `llama-server` and through Arc Llama to
  confirm routing does not lose content or alter finish reasons.

### Acceptance criteria

- Ordinary clients receive a clean final answer from the supported test models.
- Reasoning-enabled clients can distinguish reasoning from the final answer.
- Streaming and non-streaming responses agree on content, reasoning, usage,
  and finish reason.
- Cancellation closes the upstream response and frees the inference slot.
- Existing OpenAI-compatible clients continue to work without custom parsing.

## Phase 5: regression, migration, and package hardening

### Automated validation

Run on Python 3.10, 3.12, and 3.14:

```bash
ruff check src tests registry-repo/scripts
mypy --check-untyped-defs src
pytest tests/ -q --tb=short -p no:cacheprovider
python -m build
```

Add or retain coverage for:

- Configuration migration from every documented 0.x schema still in use.
- Concurrent requests during load, eviction, cancellation, and shutdown.
- Restart after a model crash or failed speculative draft.
- Runtime checksum mismatch, unsafe archives, and interrupted installation.
- Oversized or malformed community registries and atomic rollback.
- Hostile Markdown, unsafe URLs, and raw HTML in model output.
- Offline loading of the model manager and chat UI.
- Wheel installation without optional `agent`, `mcp`, `tui`, or embedding
  dependencies.
- Windows paths, process creation, DLL discovery, console encoding, and process
  termination.

### Package inspection

- Build both the source distribution and wheel from the release tree.
- Install the wheel in a new Python 3.10 environment without extras.
- Confirm the package includes static UI files, vendored browser assets and
  licenses, recipes, and documentation required at runtime.
- Confirm the archives exclude virtual environments, model files, benchmark
  output not intended for release, caches, logs, tokens, and local absolute
  paths.
- Run all public CLI `--help` commands from outside the repository.

### Acceptance criteria

- The complete automated suite passes from a clean checkout.
- The bare wheel serves both web pages without network access.
- A 0.8 configuration starts successfully or reports an explicit migration
  action without losing data.
- Repeated start/stop and model-switch tests leave no child processes or ports.

## Phase 6: release-candidate stabilization

### RC preparation

- Change the version from `0.9.0.dev0` to `0.9.0rc1`.
- Convert the changelog's `Unreleased` section into a dated RC section and make
  sure every user-visible behavior change is represented.
- Publish GitHub release notes that state the supported scope, experimental
  scope, upgrade path, known limitations, and hardware results.
- Publish signed or otherwise verifiable wheel and source-distribution hashes.
- Install the published artifact, rather than a local wheel, for the final
  smoke test.

### Stabilization period

Use a minimum fourteen-day RC period. Restart the clean-day count after any
release-blocking fix.

- Days 1–3: installation, model registration, and first-run focus.
- Days 4–7: continuous use through the web UI and at least one external
  OpenAI-compatible client.
- Days 8–10: model switching, long-context requests, cancellations, and failure
  recovery.
- Days 11–14: upgrade/downgrade, package inspection, documentation walkthrough,
  and final regression run.

Publish `rc2` when a fix changes runtime installation, configuration, routing,
response normalization, process lifecycle, or security-sensitive behavior.

### Defect policy

- **Release blocker:** data loss, unsafe archive or registry handling, secret
  exposure, install failure on a supported clean host, inference failure on a
  supported configuration, incorrect routing, broken streaming, orphaned model
  processes, or incompatible configuration migration.
- **Must fix or document before 1.0:** confusing but recoverable first-run
  failure, incorrect resource estimate, significant UI failure, or a supported
  client requiring an undocumented workaround.
- **May defer:** experimental-feature defects, cosmetic issues, additional GPU
  policies, new integrations, and performance improvements without a
  correctness impact.

### Acceptance criteria

- No unresolved release blockers.
- At least seven consecutive days without a release-blocking code change.
- All must-fix issues are closed or have an explicit documented limitation.
- The final RC artifact passes the full release checklist without local patches.

## Phase 7: publish 1.0

- Promote the final RC code without feature changes.
- Set the version to `1.0.0`, date the changelog, and update installation
  examples that still reference development versions or ports.
- Build in a clean environment and record artifact hashes.
- Run the Linux and Windows CI matrix and the bare-wheel jobs.
- Install the produced wheel on a clean supported machine and run one final
  streaming and non-streaming inference request.
- Publish to PyPI, create the GitHub release, and verify installation from PyPI.
- Keep the previous stable package and migration instructions available for
  rollback.

## Suggested implementation order

The phases are deliberately ordered by risk:

1. Baseline and organize the current work.
2. Complete first-run behavior.
3. Add fast preflight failures and useful diagnostics.
4. Stabilize reasoning and response fields.
5. Finish migration, lifecycle, browser, and package regression coverage.
6. Complete the external hardware matrix.
7. Publish and soak `0.9.0rc1`.
8. Promote the proven RC to `1.0.0`.

First-run and diagnostics should be completed before the RC because they affect
how every later test is interpreted. Response normalization should be frozen
before external client testing so RC feedback reflects the intended 1.0 API.

## Recommended issue breakdown

Create focused tracking issues for:

1. Clean first-run scenario harness.
2. Idempotent and interruptible runtime/model setup.
3. Model and draft path preflight validation.
4. Structured startup failures and concise CLI/API messages.
5. Redacted diagnostics collection.
6. Reasoning/content response contract.
7. Streaming normalization and cancellation lifecycle.
8. Configuration migration fixtures.
9. Offline browser and hostile-output regression coverage.
10. Bare-wheel and source-distribution audit.
11. Supported hardware validation matrix.
12. `0.9.0rc1` publication and stabilization tracking.

Each issue should include its relevant acceptance criteria from this document.
Avoid combining unrelated improvements into the RC unless they close a release
gate.

## Work that begins after 1.0

After 1.0, development can resume on multi-GPU scheduling, richer agent and MCP
support, audio integration, additional speculative-decoding strategies, broader
GPU vendors through upstream servers, and further performance tuning. These
features should not expand the 1.0 scope during stabilization.
